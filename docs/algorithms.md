# 算法

界面上每个数字的算法。代码位置写在每节末尾。

## 1. 基本约定

- **缺失不是 0**。大神没给的数据记为缺失，不参与平均，不当 0。唯一例外是第 6 节的补全规则。
- **胜率** = 胜 ÷ （胜 + 负），平局不计入分母。没有胜负记录时为缺失。
- **KDA** = （消灭 + 助攻）÷ 阵亡。只统计消灭、助攻、阵亡三项都有的对局，累加后再相除，不是各场 KDA 的平均。
- **平均值**只计入提供了该项数据的对局；样本数少于对局数时，界面标出 n。

位置：`crates/watch-core/src/analysis.rs`、`app/lib/state/match_view.dart`（`Agg`）。

## 2. 段位和段位分

内部用 500 到 5000 的段位分，便于比较和求平均。

| 段位 | 起点分 |
|---|---|
| 青铜 | 500 |
| 白银 | 1000 |
| 黄金 | 1500 |
| 白金 | 2000 |
| 翡翠 | 2500 |
| 钻石 | 3000 |
| 大师 | 3500 |
| 宗师 | 4000 |
| 冠军 | 4500 |

每个段位分 5 个小段，数字 5 最低、1 最高，每小段 100 分：

> 段位分 = 起点分 + （5 − 小段数字） × 100

例：白金 2 = 2000 + 3 × 100 = 2300。反过来，由分数得到段位：取起点分不超过它的最大段位，小段数字 = 5 − ⌊（分数 − 起点分）÷ 100⌋（最多 4 个台阶）。

两种来源：

- **竞技、快速**：大神给段位名和小段，或给紧凑的 `rankScore`（= 段位编号 × 100 + （100 − 小段））。段位名或小段缺失时用后者还原。段位编号不按高低排（翡翠是后加的，编号排在最后）。
- **角斗领域**：段位分本身是连续分数，直接使用。

未定级的玩家大神给占位值（名称 None、分数 0），解析为没有段位。

位置：`crates/watch-core/src/dashen/normalize.rs`（`rank`、`TIER_BASES`）、`app/lib/core/models.dart`（`ratingLabel`）。

## 3. 本人打的职责

一场对局记在哪个职责下，决定“每个职责取 N 场”和对局强度的分组。

**以英雄目录里这个英雄的职责为准**，目录里没有这个英雄时才用对局列表的 `roleType`。原因：同一场对局，列表的 `roleType` 可能和详情、游戏本体不一致（黑影在列表里记成输出，详情里是支援），会让一场支援局占掉输出的名额。

位置：`dashen/normalize.rs`（`match_summary`）。

## 4. 对局强度

### 4.1 取哪些对局

每个职责取本人打这个职责的**最近 N 场**（N 为 5、10 或 20，不够就取全部）。选场用**对局页已读取的对局记录**，不另外翻列表，强度分析和对局页因此用同一份记录，也少一轮翻页请求。

范围可以只选一个职责（重装、输出或支援）：翻页只看这个职责是否凑够 N 场，选场、读详情、查段位也只针对它，请求量约为三个职责的三分之一。其余职责不分析，不出现在结果里。

1. 读最新一页，有比本机已保存的最新一场更新的对局，就读进来保存（见 4.6）。
2. 每个要分析的职责按时间从新到旧取前 N 场。职责未知的对局不选。
3. 某个职责不够 N 场，且本机保存的列表还没到最早一场，就往更早读，直到够或读完；读完仍不够就取全部。
4. 选好的对局记录原样交给服务。服务不读列表，只读这几场的详情（双方各 5 名玩家）并取段位，不再按“每个职责 N 场”截一次。
5. 一场里没有任何玩家评得出段位时，这场不计入场数和平均，但留在逐场图和明细里，显示为空（无人定级）。某个职责因此少于 N 场时，从已读取的对局里多取几场再来一轮，最多 8 轮；已读过的详情和快照都在本机，多一轮很便宜。这个职责已保存的对局用完了，才读更早的对局；读完仍不够就取全部。

位置：选场在 `app/lib/state/app_state.dart`（`runStrength`、`pickPerRole`）；服务端收到 `known_matches` 时不翻页（`crates/watch-core/src/collect.rs`）。命令行和没有传入记录的调用，仍由服务自己翻页并选场（`match_pages_until`、`role_quota_met_for`、`select_per_role_for`）。

### 4.2 每名玩家的段位分

**段位快照**（1.4.0 起，`crates/watch-core/src/snapshot.rs`）：大神只给玩家现在的段位，所以读取一场对局时，查一次每名参与者**本赛季竞技**三个职责的段位，存进这场对局（`Participant::career`）。每个职责是三种状态之一：

| 状态 | 含义 |
|---|---|
| 有段位 | 本赛季这个职责有段位 |
| 没有段位 | 本赛季这个职责没有段位；不看往期赛季 |
| 查询中 | 还没查到，或请求失败；由后台任务重新排队再查（见 4.6），不当作没有段位 |

已知的职责之后不再变：同一场对局什么时候打开，阵容的段位都一样。每名玩家一次请求，大神第一次答复为空时按赛季号再问一次；同一次分析或同一个后台任务里一名玩家只查一次（`snapshot::Lookups`），不同任务之间不复用。1.4.0 之前存下的对局没有快照，后台补取时按补取当天的段位记。

**显示和计算用哪个段位**，只在 `crates/watch-core/src/rank_view.rs` 一处决定，对局表、对局强度、同分段对比用的是同一个结果。按顺序取第一个成立的：

1. 对局自带段位（竞技、角斗领域提供）：用它。
2. 快照里所打职责有段位：用它。
3. 快照里所打职责还在查询中：查询中。
4. 所打职责没有段位（或职责未知）：其他职责都已知后，取其中**最高**的段位；其他职责还有查询中的，显示查询中；都没有段位，未定级。

角斗领域没有竞技段位可查，没有玩家编号的玩家查不了，这两种只看对局自带段位。

第 4 条让一局的强度不只看恰好有这个职责段位的几个人。按其他职责计的人数单独统计，强度图的悬停写“其中 N 人无该职责段位，按其他职责最高段位计”，对局详情的段位徽标也注明。这名玩家在分职责的平均里仍算在他这一局所打的职责下。

未定级和查询中的玩家不计入，不当 0。

一次分析查询的玩家数有上限（界面传 N × 30，最多 600），超出的不查。

### 4.3 一场的强度

对己方和对方分别、对四个“槽位”（综合、重装、输出、支援）各算一组：

- 综合 = 这一队所有已定级玩家的平均；重装、输出、支援 = 这一队里打那个职责的已定级玩家的平均。
- 每个槽位另记**最低分、最高分**和已定级人数。
- 差 = 己方平均 − 对方平均，正数表示己方更强。两队合起来的平均记为全场。
- 一场里没有任何已定级玩家，这场不进入强度分析。

### 4.4 汇总

按本人所打职责分组，模式之间不混（角斗领域的段位是另一套）：

- 战绩：场数、胜、负、胜率。
- 每个槽位的己方、对方、全场、差：各场平均值的平均，每场权重相同。

### 4.5 走势图

- 每场一个点：这一场己方和对方的综合平均。
- 竖条是这一队已定级玩家的最低到最高分，点是平均。
- 职责筛选按本人所打职责过滤对局，没打过的职责不显示。
- 纵轴：数据跨度不超过 900 分时每 100 分（一个小段）一格，否则每 500 分（一个大段）一格；刻度标段位名，悬停显示平均分数和区间。
- 中间缺数据的对局：前后两个有数据的点之间画斜线阴影带，不连线。

位置：`crates/watch-core/src/strength.rs`、`app/lib/ui/pages/strength_page.dart`、`app/lib/design/charts.dart`。

### 4.5.1 当前赛季

大神只说“当前赛季”，不说是第几季；按赛季号查询时，没开始的赛季返回空数据。2026-10-21 实测：不带赛季、第 25 赛季、第 26 赛季三次查询，前两次完全相同，第三次为空。

判断方法：

- 起点是目录里最新的赛季。
- 服务每次运行，第一次读到某名玩家有对局的当前赛季生涯时，按赛季号再查一次下一季。
- 两份数据（各职责、各队列的战绩）完全相同，说明大神已经换季，当前赛季前移一季。只前移，不后退；查询失败时下次读生涯再试。

内置目录没更新时，段位仍记在正确的赛季下，赛季走势也能读到新赛季。

不带赛季的当前赛季生涯有时为空，而按赛季号查同一季不为空（2026-10-23 竞技实测），这时档案页按赛季号再问一次。

分天、分小时（今天、昨天、时段胜率）按北京时间（UTC+8）计算，国服服务器、大神和玩家都在这个时区。1.2.0 及以前误用了东京时间（UTC+9）。

### 4.6 本地数据库

读到的东西存在本机（`matches.db`，表结构见 [architecture.md](architecture.md)），下次直接用，不再请求大神。

| 内容 | 键 | 保留多久 |
|---|---|---|
| 对局列表 | 被查询的玩家 + 模式 + 赛季 | 一直保留，只增不改 |
| 对局详情（含双方全部玩家和每人的段位快照） | 模式 + 对局编号 + **被查询的玩家** | 存了超过 180 天的在启动时清掉。对局结束后不到 1 小时读到的详情可能不完整：存下 10 分钟后再用时重新读取并覆盖（已取的快照保留），直到存下一份对局结束 1 小时后读到的 |
| 往期赛季的生涯（赛季走势页） | 被查询的玩家 + 模式 + 赛季 | 已结束的赛季读一次就一直用；当前赛季每次都读 |
| 参赛记录 | 从详情里拆出，按玩家编号可查 | 跟着详情走 |

段位不单独存：快照就在对局详情里（4.2）。1.4.0 之前的段位缓存 `ratings.db` 在启动时删除。

**对局列表的增量读取**：

1. 先读第 1 页。页里的对局都已保存，说明没有新对局，到此为止（一次请求）。
2. 有没保存的，就继续读第 2、3 页……直到某一页出现已保存的对局，新旧接上；新对局保存下来。
3. 本机保存的列表还没到最早一场时，从保存的末尾往更早读，直到满足要求（每个职责够 N 场）或读完。对局页要求读完全部，强度分析只要求够用。
4. 每次调用最多读 10 页，没读完就返回，下一次调用接着读，界面边读边显示。
5. 保存的列表始终是从最新一场开始、没有缺口的一段：新对局多到读完预算也接不上已保存的部分时，丢掉旧的，只保留新读的一段，再从那里往更早补。宁可多读，不留缺口。

实测一个账号的快速比赛列表读到第 9 页就读完，共 99 场：大神只保留最近这些。

**后台补段位快照**（1.4.0 起，`crates/watchd/src/background.rs`）：

1. 对局列表更新后，界面请服务给这个玩家和模式排一个任务（`POST /api/ranks/start`）。后来开始的任务排在前面。
2. 任务在最新 300 场里找出快照还没填满的对局，从新到旧每次取 3 场：读详情，查能查的参与者本赛季的段位，存进对局。
3. 有其他查询时，任务在下一个请求前暂停让路，空闲 1.5 秒后继续。
4. 查询失败的对局重新排队：这一轮放到队尾，先做后面的；只剩失败的时，等 30 秒、60 秒、120 秒各重试一轮，失败的玩家重新再问；三轮之后剩下的保持查询中，等下次刷新列表再开始。
5. 进度就是已存的快照，任务中断（服务重启、会话过期）后再开始，从停下的地方继续。

打开一场对局的详情时，单独把这一场的快照补齐（`POST /api/player/prepare`）。

**其他规则**：

- 详情按被查询的玩家分开存：详情里的己方、对方和胜负都相对这名玩家，换一个人查同一场，两队是反的。
- **别人的令牌不落盘。** 一场详情已存、但快照还缺某些玩家时，重新读这一场详情取令牌，再查这些玩家。
- 大神没给令牌、查不了的玩家记在这场详情里，下次不为他们反复请求。
- 刷新只跳过 30 秒内的请求复用（第 8 节）；已存的对局详情、已知的快照和往期赛季的生涯照常使用。
- 读写本地数据库失败只让这一项走网络，不让分析失败。

**减少请求和等待的做法**（真实账号上量过）：

- 1.4.0 起不查往期赛季的段位，也不单独缓存段位。真实数据（快速比赛 245 场，2293 人次要查段位，2050 名不同玩家）里，跨 1 小时复用段位只省约 9% 的请求，几乎都来自固定队友；同一后台任务里一名玩家只查一次，已拿到这部分。
- 准备对局、对局强度分析这类只要对局和段位的调用，不读玩家卡片和生涯（`profile: false`），每次少 3 个请求；数据都已准备好时，对局强度分析从约 1 秒降到约 0.03 秒。
- 刷新按钮和分析几乎同时要读最新一页时，10 秒内只读一次。
- 启动时先显示本机已保存的对局（不发请求，约 15 毫秒），再查玩家身份和新对局（约 1 秒）；查过一次的昵称记在本机。
- 试过把卡片、生涯和对局列表同时请求：大神对同一个账号像是逐个答复，没有变快，没有保留。
- 请求速度已接近每秒 5 次的上限（实测 4.6 次/秒，单个请求中位数约 200 毫秒），再并发也不会更快；提高上限有被限流的风险，没有改。

实测（35 场重装的账号，用对局页已读的 36 场，重装取最近 5 场）：第一次 87 次请求、65.2 秒；第二次 0 次请求、1.5 秒，87 项全部来自本机，结果一致。重装取到已读的全部 11 场时，只为新增的 6 场请求。

**Fleta 指数**（对局详情里每名玩家一个）：本人最后一击 ÷（本队最后一击合计 × 0.5）× 100%。100% 表示拿下本队一半的最后一击。只看这一场、只和本队比，所以辅助和重装通常偏低、输出偏高；最后一击未知或本队没有最后一击时不给数值。公式来自参考项目，后端算好（`analysis::attach_fleta`），打开详情时附上，不存进本地数据库。

位置：`crates/watch-core/src/cache.rs`（接口）、`crates/watchd/src/store/`（SQLite 实现）、`collect.rs`、`snapshot.rs`、`crates/watchd/src/background.rs`。

## 5. 请求预算

一次分析的请求数大致是：

> 取到的对局数 + 需要查的玩家数 × 1 到 2（对局不够、要多读列表时另加翻页）

N = 10、三个职责都够场时，约 30 场、300 名玩家，几百次请求；只选一个职责约三分之一。并发上限 2、每个账号每秒 5 次，第一次要一两分钟。之后再分析只读新对局和快照还缺的玩家；后台任务通常已经把它们补齐。

## 6. 英雄数据的补全

大神的英雄统计常常缺项，界面的英雄数据按下面的规则补全。数据来源是 `queryCountInfo` 里每个英雄的两组数：每场平均和每 10 分钟（后者大神只给 3 到 8 项）。

### 6.1 这个英雄能不能产出某项

满足任一条即为能产出：

- 游戏给这个英雄定义了这项统计（目录里的统计清单）；
- 大神这次返回了这项；
- 本机已读取的对局里，这一项有数值（对局里的消灭、阵亡、助攻、伤害、治疗、阻挡）。

另外有两条固定规则：**消灭、阵亡、助攻、伤害人人都能产出**；**支援职责一定能产出治疗**。治疗还认两类别名：自我治疗量，以及英雄专属的治疗量（如某某权杖治疗量）。

### 6.2 缺项怎么填

| 情况 | 每场平均 | 每 10 分钟 |
|---|---|---|
| 大神给了 | 用大神的 | 用大神的 |
| 每场有、每 10 分钟缺 | — | 每场平均 × 600 ÷ 场均时长（秒），标 ≈ |
| 每场缺，但已读取的对局里有 | 取这些对局的平均，标 ≈ | 同上公式推算，标 ≈ |
| 能产出，哪里都没有 | 0（灰色） | 0（灰色） |
| 不能产出 | — | — |

场均时长优先取大神的“累计游戏时间”每场平均，没有则用总时长 ÷ 场次。

公式的依据：金驭每场消灭 15.8，场均 432 秒，推算 15.8 × 600 ÷ 432 = 21.9，与大神给的每 10 分钟值一致。

不参与推算：各种率（命中率、使用率）、累计游戏时间、英雄获胜、平均类数值，它们按每 10 分钟没有意义。

### 6.3 其他细节

- 命中率等率类数值大神给 0 到 1 的小数，界面乘 100 显示为百分比。
- 目录里个别统计项登记了两次、名称相同：名称和每场数值都相同的只显示一次。
- **阻挡**：游戏的统计清单里没有这一项，只能由已读取的对局推算：每场平均 × 600 ÷ 场均时长。重装没有数据时是 0，其他职责只有对局里出现过才显示，否则是 —。
- 英雄列表里“消灭、伤害、治疗、阻挡 /10分”用同一套规则。

位置：`app/lib/core/hero_stats.dart`、`app/lib/core/models.dart`（`HeroUsage.per10For`）、`app/test/hero_stats_test.dart`。

## 7. 其他计算

### 7.0 成长面板

每局算五个值：存活时长、Fleta 指数、KDA、治疗量、阻挡量，并读它们的走势。不足 120 秒、没有阵亡数或没有开始时间的对局不计入。

**存活时长。** 大神只给每局的阵亡次数，不给阵亡时间点，所以按总量平均：阵亡间隔 = `duration_s ÷ deaths`（承受风险的总时间除以事件数，只知道总数时估计事件间隔的常规办法）。没有阵亡的对局取整局时长，标为 `deathless`：真实值至少这么长。重生等待含在每个数里，每局一样，不影响比较。最后一次阵亡之后到对局结束的那段也算在内；大神若给出阵亡时间点，可以改成精确值。

**KDA。** `(kills + assists) ÷ max(deaths, 1)`，没有阵亡按 1 次算（同样标 `deathless`）。

**Fleta 指数。** 算法同对局详情（4.6），取本人每局的值。

**治疗量、阻挡量。** 折成每 10 分钟（`值 ÷ 对局时长 × 600`），长短不同的对局才能比。治疗量只算打支援的对局，阻挡量只算打重装的对局：其他职责的这两项是副产品，大多接近 0，混进来只会拖动趋势。当前职责没有这项数据时不画这张图。

**走势。** 每个指标按时间排好后用两种读法：

1. 前后半段：分成较早一半和较新一半（场次为奇数时中间一局不算），比较平均值，给出差值、百分比和对局序号上的最小二乘斜率。
2. Mann-Kendall 趋势检验：对所有 `i < j` 的对，后面的比前面大记 +1、小记 −1，求和得 S；方差 `n(n−1)(2n+5)/18`（有并列时按并列组扣减）；`z = (S − sign(S)) / √方差`；双侧 `p = erfc(|z|/√2)`。不假设数值的分布。`p` 是原假设（没有单调趋势）成立时出现当前或更极端统计量的概率。`p < 0.1` 记为上升或下降（看较新一半比较早一半大还是小），否则记为无变化。不足 8 场不检验。

“全部”和每个职责各算一次。不同职责的数值本来不同（支援比重装活得久，输出的 Fleta 更高），换职责会让“全部”变化而每个职责自己没变，所以以分职责的结果为准。

位置：`crates/watch-core/src/growth.rs`（测试：一次阵亡的间隔、没有死亡、KDA 与 Fleta、缺失不当零、不可用对局、时间顺序、上升/下降/平稳、换职责不算成长、MK 的已知值），接口 `POST /api/player/growth`，界面 `app/lib/ui/pages/growth_page.dart`；折线图的盾牌标记在 `app/lib/design/charts.dart`。

### 7.1 统计口径（所有页面共用）

战绩样本小、波动大：8 场 87.5% 和 64 场 67% 不是同一种数字，前者很可能只是一个 55% 的玩家打了顺风的一周。规则统一放在 `crates/watch-core/src/stats.rs`，界面只读结果。

| 规则 | 内容 |
|---|---|
| 样本门槛 | 英雄、地图等分组少于 **5 场**（已分胜负的场次）不参与比较和排名，照常列出并标“样本不足”。趋势少于 **8 场**不检验。门槛由 `/api/state` 的 `thresholds` 提供 |
| 置信区间 | Wilson 区间（95%）。不会超出 0–100%，0 胜或全胜时也不会缩成一个点。每个分组战绩都带 `win_rate_low_pct`、`win_rate_high_pct` |
| 排序 | 按胜率排序时用**区间下限**。7 胜 8 场（下限约 53%）排在 43 胜 64 场（下限约 55%）后面。界面显示的仍是胜率本身，悬停看区间 |
| 走势的措辞 | 先写方向和幅度（“前后半段 +18%”），再写可信度：Mann-Kendall p < 0.05 为“显著”，p < 0.1 为“弱趋势”，否则“无变化”，不足 8 场为“样本不足”。p 值放在悬停说明里 |
| 个人基线 | 成长图的灰色底带：这一局之前 20 场（至少 8 场）的第 1 到第 3 四分位。落在带外的一局才算反常 |

大神给的英雄赛季胜率是“胜 ÷ 场次”（平局在分母里），和本工具的“胜 ÷（胜 + 负）”不同；英雄页的区间按大神的口径算。

### 7.2 同分段基准（英雄详情的“同分段对比”）

本机每存一场对局，就有另外 9 名玩家的数据，大多数带段位（对局自带，或段位快照，按 4.2 的同一规则取）。这是国外工具拿不到的国服样本，`crates/watch-core/src/benchmark.rs` 用它比较：本人用这个英雄，和段位相近、用同一英雄的其他玩家相比。

| 项 | 规则 |
|---|---|
| 比什么 | 每场的每 10 分钟数据：伤害、治疗、阻挡、消灭、最后一击、阵亡。取本人这个英雄的**中位数**，和同分段的每一场比，得到百分位（并列算一半），单场起伏不左右结果。阵亡越少越好，百分位反过来算 |
| 分档 | 后 10%、10–30%、30–70%、70–90%、前 10% |
| 同分段 | 同一模式、同一英雄。先取本人所在段位（这个职责最新一场对局自带的段位，没有则取最新的快照）；不到 30 场放宽到相邻段位；再不够不限段位。界面写明用了哪一档、多少场。本人少于 3 场不比 |
| 跳过 | 短于 2 分钟的对局；角斗领域（段位自成一套）；本人为 0 且同分段中位数也为 0 的指标（比如支援的阻挡） |
| 偏差 | 样本只来自这台电脑上查过的玩家所在的对局，不代表全服，界面写明 |

接口 `POST /api/player/benchmark`，不向大神请求。

档案页“近期表现”另有全服参考：大神给的全服场均（`serverMapCountData`），写在本人的场均下面。它是全服平均，不分段位。

### 7.3 近期动态（概览页）

`crates/watch-core/src/insights.rs` 从概览的数字里挑出证据够硬的几条，最多 5 条，按下表顺序。服务只给种类和数字，措辞在 app 的字符串表里。

| 条目 | 条件 |
|---|---|
| 连胜中 / 连败中 | 到现在为止连续 3 场及以上同一结果 |
| 连败时对方更强 | 连败的几场里，有详情、能算对局强度的至少 3 场，其中超过一半对方平均段位分高出己方 200 分（两个小段）以上。没有强度数据不说 |
| 状态回升 / 下滑 | 近 20 场和之前 20 场的胜率相差 15 个百分点以上，两边各至少 10 场分出胜负 |
| 回升 / 下滑来源 | 有上一条时，比较两段里每张地图、每个英雄的净胜（胜场减负场），取变化方向和状态一致、变化至少 2 的最大两项；点击筛选对局列表 |
| 强势图 / 苦手图、绝活 / 短板英雄 | 置信区间（7.1）整体高于或低于本人总胜率，场次够门槛。地图、英雄各取偏离最大的一个 |
| 连续第 4 场起胜率下降 | 一次连续游戏（相邻两场间隔不超过 5 小时）有 4 场以上时，第 4 场起的胜率和前 3 场比；两边各至少 10 场分出胜负，双比例检验 p < 0.10。只说下降这一个方向 |
| 同分段偏低 / 偏高 | 在最常用、有同分段基准（7.2）的英雄上，最弱的一项低于第 25 百分位说偏低；否则最强的一项高于第 75 百分位说偏高 |

每类都可以屏蔽，设置存在本机；页头显示“已屏蔽 N 类”，可以取消屏蔽。

### 7.4 地图（地图页）

`crates/watch-core/src/maps.rs`。地图类型取自大神目录 `mapList[].mode`，目录里没有的地图归入“其他”，排在最后；其余类型按场次从多到少。

- 每类地图里，场次够门槛（7.1，分出胜负至少 5 场）的地图按置信区间下限从高到低排；样本少的地图排在后面、按场次排、变灰。
- 平均时长只用存了详情的对局（列表没有时长），写明是多少场。
- 每张图列出最常用的 5 个英雄及各自战绩。
- 对局列表不区分进攻和防守，所以不按攻防拆开。

### 7.5 角斗领域构筑

`crates/watch-core/src/stadium.rs`，只用本机已存的角斗领域对局详情，不和其他模式混算。

- **样本**：“本人”只算本人的对局；“本机所有玩家”算这些对局里的每一名玩家，每人每场一次，胜负按其所在一方。界面写明样本多少、其中多少是本人的。
- **第几回合选的**：一个异能或物品第一次出现在某名玩家回合名单里的那个回合，统计取最常见的回合。没有存回合数据的对局不计回合。
- **排序**：分出胜负至少 5 场的条目按置信区间下限从高到低；其余排在后面、按选取次数排、变灰。
- **组合**：一场里选的全部异能当作一个组合（不计顺序），每个英雄列最常见的 6 个，各带胜率。
- **回合胜负**：回合比分是累计值（两边相加等于已打回合数）时，按己方比分是否增加判断；否则比较这一回合的双方比分。
- **下钻**：每个条目列出用它的对局（最多 20 场，最新在前）。

### 7.6 段位轨迹（赛季走势页）

`crates/watch-core/src/ranks.rs`，只用本机已存的对局列表和详情。

- **点**：每场带段位分（`skill_rating`）的对局一点，按职责分开；没有段位的对局（快速比赛、定级中）不画。竞技和其他模式各自一条，不混算。
- **赛季**：对局列表不带赛季。取赛季走势里各赛季的生涯场次（各职责相加），从最新一场往回数：最新的 n 场归本赛季，再往前 m 场归上赛季，依此类推；数完已知赛季后剩下的对局不标赛季。分界画在换赛季的两场之间。生涯场次与列表不一致时（列表有缺口）分界有偏差，界面写明是推算。
- **掉分**：同一职责、同一赛季内，从一个高点一路不升到下一个低点，累计掉 100 分（一个小段，`DROP_POINTS`）以上算一段。列出最近 3 段，每段写几胜几负，以及其中有对局强度（4.3）的几场里对方平均段位分减己方平均段位分的均值。
- **下钻**：图上每一点、每一段的最后一场都能打开对应对局。

### 7.7 常遇玩家与组排（常遇玩家页）

`crates/watch-core/src/party.rs`，只用本人在这个模式下已存的对局详情。

- **组排**：同队某人和本人出现在对方的 `friendBnetIds` 里（任一方列出即可）。一场的组排人数是本人加上和本人组队的人数。
- **常遇玩家**：按 bnet_id（没有时按名字）合并，至少共同出现 2 场，最多列 50 人；按共同场次、组排场次、最近一次排序。
- **共同对局**：与某名玩家的所有共同对局，各写双方的英雄和数据；“其他对局”是本人其余已存对局（包括和他对面的），“对面时”单独再列一次。

### 7.8 每日总结（每日总结页）

`crates/watch-core/src/daily.rs`，只用本机已存的对局列表和详情。

- **哪一天**：按北京时间（UTC+8）的自然日分组；默认最近有对局的一天。
- **连着打**：同一天里相邻两场间隔不超过 5 小时算同一次。
- **游戏时长**：这一天存了详情的对局的时长相加，写明是几场里的几场。
- **段位变化**：每个职责这一天最后一场的段位分，和这个职责此前最后一场（没有就用当天第一场）比。
- **高光**：

  | 项 | 规则 |
  |---|---|
  | 全场最高 | 对局列表的全场最高标记（消灭、伤害、治疗、阻挡） |
  | 单场最高 | 这一天的最大值；超过此前所有已存对局（至少 20 场）记为刷新纪录 |
  | 连胜 | 至少 3 场 |
  | 零阵亡 | 阵亡为 0 |
  | 最好的一局 | 赢下的对局里 KDA 最高的 |
  | 最高 Fleta | 需要存了详情 |

- **和平时比**：这一天场次最多的职责，这一天的场均和之前 30 天同职责的场均（至少 5 场）比。

### 7.9 其他

- **熟练度徽章**：`hero_level` 小于 25、50、75、100 分别是 1 到 4 档，100 及以上是第 5 档（灰、绿、蓝、紫、橙）。
- **队内最高值**：只比较同队里已给出的、大于 0 的数值；并列的都标；全是 0 或全缺失不标。
- **数据条长度**：按全场 10 人该项的最大值缩放，数字永远显示。
- **英雄列表的竖条颜色**：胜率 ≥ 50% 为绿，否则为红；场次少于 5 场为灰，胜率数字也变灰。

## 8. 请求策略

| 项 | 值 |
|---|---|
| 并发 | 最多 2 个请求同时进行；排队容量 8 |
| 限速 | 每个账号每秒最多 5 次 |
| 超时、重试 | 单个请求 15 秒（连接 5 秒），排队加请求合计不超过 30 秒；最多尝试 3 次，间隔 0.25 秒、0.5 秒递增 |
| 失败处理 | 401、403：停用这个凭据直到更新；429：按服务端的 Retry-After 等待；服务端错误：重试；其他 4xx：不重试 |
| 一次采集 | 超过 180 秒中止并报错，已完成的部分不会丢 |
| 同一玩家的重复请求 | 30 秒内相同请求直接复用，每个玩家最多保留 32 条；刷新时不复用 |
| 段位快照的后台任务 | 其他查询进行中时让路，空闲 1.5 秒后继续；失败的对局等 30、60、120 秒重试，见 4.6 |
| 本地数据库 | 对局列表、对局详情（含段位快照）、往期赛季生涯保存在本机，见 4.6 |

## 9. 进度显示

长操作（对局强度分析）带一个客户端生成的编号发起；后端在采集过程中记录当前阶段，界面每 0.6 秒查询一次。

| 阶段 | 记录 |
|---|---|
| 读取对局列表 | 本次读的页数、已有场数 |
| 读取对局详情 | 已读场数、当前地图 |
| 查询参与者段位 | 已查人数、当前玩家 |
| 整合计算 | — |

另外记录已发出的请求数、失败数和取自本机的项数。

“约剩”时间 = 当前阶段已用时间 ÷ 已完成数 × 剩余数，至少完成 2 项后才显示。

位置：`crates/watch-core/src/progress.rs`、`crates/watchd/src/service.rs`（`/api/progress`）、`app/lib/state/app_state.dart`。
