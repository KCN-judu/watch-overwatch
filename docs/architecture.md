# 架构

## 总体结构

```
Flutter 界面 (app/)  ──HTTP, 仅本机──▶  watchd (Rust)  ──HTTPS──▶  网易大神接口
                                         │
                                         ├─ watch-core：调度、转换、采集、分析
                                         └─ 目录：英雄、地图、统计项、段位图标
```

- 界面启动时找到并拉起 `watchd.exe`，设置 `WATCHD_EXIT_ON_STDIN_EOF`，窗口关闭时服务一并退出。
- 找服务的顺序：环境变量 `WATCHD_PATH` 指定的文件存在就用它；否则从界面所在目录逐级向上找 `watchd.exe` 和 `target\{release,debug}\watchd.exe`，取修改时间最新的一个。
- 端口：界面拉起的服务用 18280，单独运行的 `watchd.exe` 默认 18180；界面和服务都读 `WATCHD_PORT`，界面把自己的端口传给它拉起的服务。
- 服务只接受 `127.0.0.1` 或 `localhost` 的请求；非 GET 请求必须带头 `x-watch-client: watch-overwatch`，来源（如有）必须是本机，防止网页对它发请求。
- 服务在 `/` 仍提供旧网页界面（`ui/`），见 [旧网页界面的退役](legacy-ui.md)。
- 示例玩家只在开发版里有（`watch_core::DEMO_AVAILABLE`，`/api/state` 的 `demo`），发布版不带。

## 数据流

> 大神原始 JSON → `dashen::normalize` → IR → `analysis` / `strength` → 界面或导出

### 统一数据结构（IR）

界面和导出都读 IR，不读大神的原始 JSON。当前版本 `IR_VERSION` = 2.0.0（`crates/watch-core/src/ir.rs`）。类型、约定（缺失用 `null`、引用不靠名称）和请求的大神接口见 [数据结构](data-model.md)。

### 目录

内置快照 `crates/watch-core/data/query_tool.min.json`，包含英雄（图标、立绘、横幅、职责）、地图（图、玩法）、统计项清单（每个英雄有哪些统计）、威能、段位和荣誉图标。可用 `watchd import-catalog` 导入新版，也可用 `cargo xtask slim-catalog <完整文件> <输出文件>` 把完整的目录精简成快照。目录通过 `/api/catalog` 提供给界面。

## 本机接口（`watchd`）

路径、请求、返回和约定（只接受本机、会话、错误码）见 [本机接口](http-api.md)；命令行见 [命令行](cli.md)。会话只存在内存里，一小时过期，过期后界面自动重新查找。

## 界面（`app/lib`）

| 目录 | 内容 |
|---|---|
| `core/` | 数据模型（IR 的镜像）、接口调用、目录、英雄数据补全（`hero_stats.dart`）、游戏资料（`gamedata.dart`）、图片仓库（`image_store.dart`） |
| `design/` | 设计令牌（颜色、字体、间距）、形状（斜切、切角、六边形底纹）、表格、卡片列表、图表、图标和图片组件；视觉规则见 [界面设计](ui-design.md) 第 7 节 |
| `l10n/` | 字符串表：界面上的每一句话都在这里，页面不写字面量 |
| `state/` | 应用状态（每个玩家一个工作区，保存当前页、筛选、滚动位置和打开的对局或英雄）、命令注册表（菜单、快捷键、命令面板共用） |
| `ui/` | 外壳、玩家库、各页面 |

## 存放位置

数据目录是 `%LOCALAPPDATA%\Watch Overwatch`；设了环境变量 `WATCH_DATA_DIR` 时用它（界面和服务都读，脚本和截图用一个临时目录）。

| 内容 | 位置（数据目录下） |
|---|---|
| 账号凭据 | `secrets.json` |
| 界面状态（主题、行高、布局、上次的玩家和页面） | `ui-state.json` |
| 玩家库 | `players.json`，由 `watchd` 维护 |
| 图片缓存 | `img-cache\` |
| 本地数据库 | `cache\matches.db`（SQLite） |

## 本地数据库

只有一个文件 `matches.db`。1.4.0 之前另有段位缓存 `ratings.db`；现在段位存成对局里的快照，旧文件在启动时删除。

| 表 | 内容 |
|---|---|
| `match_list`、`list_state` | 每个玩家、每个模式、每个赛季的对局列表，以及是否已读到最早一场 |
| `match_detail` | 对局详情（键：模式、对局编号、被查询的玩家），含双方全部玩家和每人三个职责的段位快照，以及查不了段位的玩家 |
| `match_participant` | 从详情里拆出的参赛记录（哪一场、哪一方、打什么职责），按玩家编号可查 |
| `player_name` | 昵称（小写）对应的玩家编号，启动时不等大神答复就能先显示已保存的列表 |
| `player_profile` | 每名玩家最后一次读到的档案 |
| `past_career` | 已结束赛季的生涯（赛季走势页用），读一次就一直用；当前赛季不存 |

里面有其他玩家的昵称和编号（对局详情里本来就有），没有任何令牌。保留规则见 [algorithms.md](algorithms.md) 4.6。设置页可以查看大小和清除。

对局列表增量读取：先读第一页，发现比已保存的最新一场更新的对局，就往后读到接上已保存的部分为止；没有新对局时只有这一次请求。已保存的部分始终是从最新一场开始、中间没有缺口的一段。

**代码划分**（`crates/watchd/src/store/`）：整个程序只有这里有 SQL，每类副作用只有一个归属。

| 文件 | 职责 |
|---|---|
| `sql.rs` | 所有语句。表先声明成数据（列、主键），增删改查语句由声明生成，调用处不拼接；列名写错在生成时就报错；测试把每条语句放到真实表结构上预编译 |
| `db.rs` | 唯一持有连接的地方：加锁、事务（写操作全成或全不成）、失败只记日志并当作没有 |
| `matches.rs` | 有类型的读写函数，只操作传进来的连接或事务；不读时间、不碰文件 |
| `files.rs` | 路径、文件大小，搬入旧版的单文件库，删除旧的段位缓存 |
| `mod.rs` | 唯一的时间来源（`Clock`，测试里可以手动拨时间），给采集器用的 `StrengthCache` 适配 |

测试保证别的源文件里没有 SQL 或数据库库的引用。旧版的 `strength.db` 在启动时把对局搬进 `matches.db`（段位不搬），然后删除。

## 段位快照的后台任务

大神只给玩家现在的段位，所以对局读进来时就查一次参与者本赛季三个职责的段位，存进这场对局（`Participant::career`，每个职责是有段位、没有段位、查询中之一）。这件事由服务的后台任务做（`crates/watchd/src/background.rs`）：

- 对局列表更新后，界面调用 `POST /api/ranks/start` 给这个玩家和模式排一个任务，用 `POST /api/ranks/status` 读进度（等待、进行中、让路、等待重试、完成）。
- 后来开始的任务排在前面；有其他查询时，任务在下一个请求前暂停，空闲 1.5 秒后继续。
- 做完的部分已经存在对局里，所以任务可以随时中断（服务重启、会话过期），再开始时接着做。
- 查询失败的对局重新排队，等 30、60、120 秒各重试一轮。

规则细节见 [algorithms.md](algorithms.md) 4.2 和 4.6。

## 采集计划

`CollectPlan`（`crates/watch-core/src/collect.rs`）里与强度分析和本地数据库有关的字段：

| 字段 | 含义 |
|---|---|
| `roles` | 只分析哪些职责，空表示全部 |
| `list_quota` | 读列表时每个职责保存到这么多场就不再往更早读；不设就读完 |
| `known_matches` | 调用方已选好的对局记录；不空时服务不翻列表 |
| `lobby_ratings`、`max_rated_players` | 是否为参与者取段位快照，最多查多少人 |
| `profile` | 是否顺带读玩家卡片和生涯；只要对局和段位的调用设为假 |
| `cache` | 本地数据库，不序列化 |
| `lookups` | 后台任务的查询状态，同一任务里一名玩家只查一次，不序列化 |
| `max_pages` | 每次调用最多读几页；没读完时 `coverage.match_lists[].exhausted` 为假，再调一次从上次停的地方继续 |

## 图片

所有网络图片都经过同一个仓库（`image_store.dart`）：

| 层 | 做法 |
|---|---|
| 磁盘 | 下载一次就保存，文件名由地址的哈希生成；之后启动直接读磁盘 |
| 同时请求 | 同一地址同一时间只发一个请求，其余等同一结果 |
| 内存 | 解码后的图片放在框架的图片缓存里，上限 4000 张、600 MB；同一张图只解码一次，切换页面不重新加载 |
| 占位 | 图片到达前显示同样大小的占位块，带缓慢移动的高光；失败时显示文字或留空，不影响数据 |
| 预加载 | 目录到达后，后台预加载全部英雄的小图标和肖像、段位和荣誉图标；加载超过约 0.35 秒时状态栏显示进度 |

## 英雄资料和图标

英雄简介、技能、威能的名称和说明、技能和威能图标，来自本机安装的游戏，用 OWLib 的 DataTool 解包。解包方法和已整理的资源见 [game-data.md](game-data.md)；`resources/game/` 是整理后的资料，`app/assets/game/` 是打进应用的副本，用 `cargo xtask sync-assets` 同步（同时更新 `app/pubspec.yaml` 里的资源列表）。
